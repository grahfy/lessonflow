# FEAT: Expand Admin Manual Into Full End-User Manual + Automated Playwright Screenshots

## Description

Upgrade the new `/admin/manual` area from a lightweight hub into a detailed, in-app end-user manual covering the full web app workflow surface (public forms, student portal, admin bookings/customers/materials, invoices, reports, settings, and operational runbook guidance).

The manual should also gain a repeatable screenshot pipeline that automatically captures current UI screenshots using Playwright, so documentation and in-app screenshots stay aligned with the actual product UI.

## Context

The current `/admin/manual` page provides quick links, a short deploy/update runbook summary, and a small static screenshot gallery. It is useful as an entry point, but it is not yet a comprehensive end-user manual for all functions of the app.

The repo already has a detailed `Documentation/` suite and historical Playwright-captured screenshots, but screenshot capture is not yet automated in the repo tooling (`npm run test:e2e` is still a placeholder), and the in-app manual content is currently hand-authored JSX that can drift from the markdown docs.

## Requirements

### Functional Requirements
- Expand `/admin/manual` to cover all major app functions with detailed end-user guidance:
  - public website pages and booking/contact workflows
  - student portal login and materials usage
  - admin bookings/customers/learning-materials workflows
  - invoice creation/edit/send/reminder/payment/credit-note flows
  - reports console usage (daily/weekly/monthly/yearly, comparisons)
  - settings console usage (env-backed fields, restart behavior)
  - deploy/update runbook overview for operators (with clear “technical owner” labeling)
- Add in-page navigation (table of contents and/or section navigation) for fast lookup.
- Present screenshots inline with the relevant manual sections (not only a separate gallery).
- Keep documentation content maintainable with a clear source-of-truth model (avoid duplicate manual text drifting between `/admin/manual` and `Documentation/*.md`).
- Add an automated screenshot capture workflow using Playwright that can regenerate the documentation screenshots.
- Ensure screenshot automation uses safe, non-production demo/test data only.
- Provide a documented operator/developer workflow for recapturing screenshots after UI changes.

### Non-Functional Requirements
- `/admin/manual` must remain admin-authenticated only.
- Manual content should be readable for non-technical users (plain language, task-based).
- Screenshot automation should be deterministic enough to avoid churn (stable seed data, stable viewport/theme, reduced animation interference).
- Changes should preserve existing admin navigation and manual access patterns.

## Current State

- `/admin/manual` exists and is protected, but only renders a lightweight hub (`src/app/admin/manual/page.tsx:1`, `src/components/admin-manual-client.tsx:61`).
- The in-app manual content is hard-coded JSX, including a fixed screenshot list and captions (`src/components/admin-manual-client.tsx:16`, `src/components/admin-manual-client.tsx:92`).
- End-user docs already exist in `Documentation/` and include screenshot references and governance (`Documentation/README.md:60`, `Documentation/README.md:65`).
- Screenshot inventory/docs mention Playwright capture, but the process is not wired into repo scripts (`Documentation/assets/README.md:7`, `Documentation/CHANGELOG.md:6`).
- `npm run test:e2e` is still a placeholder, so there is no committed Playwright harness to automate screenshot capture (`package.json:17`).

## Desired State

- `/admin/manual` becomes a complete in-app, searchable/navigable end-user manual for the whole product (with technical operator sections clearly identified).
- The manual content is sourced from a maintainable structure (preferably shared with repo docs or generated from them).
- Screenshot assets are generated by a repeatable Playwright workflow and refreshed with a documented command.
- The in-app manual and `Documentation/` suite stay in sync through a defined update process and manifest-driven screenshot references.
